## 1. Открытый поиск перекрывает кнопку закрытия мобильного меню

**Приоритет:** высокий. **Связь с предыдущим отчетом:** Д14, раскрываемый поиск.

**Страница:** [главная](https://bhenergy.github.io/ystu-frontend/pages/index.html). Дефект находится в общей шапке; после исправления необходима проверка на остальных страницах с этим компонентом.

**Как воспроизвести:**

1. Открыть главную страницу при размере окна 390×844 px.
2. Открыть мобильное меню.
3. Нажать иконку поиска в шапке.
4. Попытаться закрыть меню его кнопкой с крестиком.

**Фактически:** поисковая форма перекрывает строку мобильных инструментов и кнопку закрытия меню. В центре кнопки меню находится `.header-search__close`; она перехватывает нажатие. Меню своей кнопкой закрыть нельзя, пока поиск открыт.

**Ожидается:** поиск и кнопка закрытия меню доступны одновременно. Закрытие меню скрывает поиск и корректно восстанавливает состояние шапки.

**Где исправлять:** [src/styles/components/header-search.css, строка 24](https://github.com/BHEnergy/ystu-frontend/blob/09dc42812ee3a0bfcd1c150778b67afb5584f972/project-ystu-frontend/src/styles/components/header-search.css#L24).

```css
@media (max-width: 1100px) {
    .header--menu-open .header-search {
        position: fixed;
        top: 96px;
        left: 0;
        right: 0;
    }
}
```

При проверке кнопка меню занимает область `x=325, y=100, width=42, height=42`. Фиксированное положение поиска `top: 96px` приводит к пересечению с этой областью. Нужно разместить форму с учетом фактической геометрии шапки и информационного баннера.

**Подтверждение:** воспроизведено в основной версии, в `dist` и на опубликованном сайте.

**Критерии закрытия:** кнопку меню можно нажать при открытом поиске; меню и поиск закрываются; работают Escape и отдельное закрытие поиска; фокус остается на доступном элементе. Проверить состояние с информационным баннером и без него, а также после прокрутки страницы.

## 2. Мобильный поиск зависит от порядка загрузки скриптов

**Приоритет:** средний. **Связь с предыдущим отчетом:** Д14.

**Как воспроизвести:**

1. Открыть главную страницу на ширине 390 px.
2. Обеспечить загрузку `header-search.js` раньше `header.js`. При проверке ответ `header.js` задерживался на 700 мс через Playwright.
3. Дождаться завершения загрузки страницы, открыть мобильное меню.
4. Нажать мобильную иконку поиска.

**Фактически:** вместо раскрытия строки происходит переход на `search.html`. При такой последовательности мобильная ссылка не получает обработчик раскрытия поиска.

**Причина:** в [src/js/main.js](https://github.com/BHEnergy/ystu-frontend/blob/09dc42812ee3a0bfcd1c150778b67afb5584f972/project-ystu-frontend/src/js/main.js#L248) компоненты загружаются параллельно через `Promise.allSettled`. В [header.js, строка 93](https://github.com/BHEnergy/ystu-frontend/blob/09dc42812ee3a0bfcd1c150778b67afb5584f972/project-ystu-frontend/src/js/components/header.js#L93) мобильные инструменты создаются через `cloneNode(true)`. В [header-search.js, строка 4](https://github.com/BHEnergy/ystu-frontend/blob/09dc42812ee3a0bfcd1c150778b67afb5584f972/project-ystu-frontend/src/js/components/header-search.js#L4) ссылки собираются один раз при запуске компонента. Позже созданные клоны не входят в этот набор; обработчики событий при клонировании не копируются.

**Что требуется:** обеспечить независимость поведения от порядка загрузки. Возможные решения — последовательная инициализация поиска после создания мобильных инструментов или делегирование событий общему контейнеру. Конкретное решение остается за разработчиком.

**Подтверждение:** воспроизведено в основной версии и `dist`, в Google Chrome и Chromium. Проверка проводилась с контролируемой задержкой ресурса; это воспроизводимый сбой инициализации, а не утверждение, что он возникает при каждом открытии сайта.

**Критерии закрытия:** при обоих порядках загрузки мобильная иконка раскрывает поиск без перехода; обработчик срабатывает один раз; закрытие поиска и меню работает корректно. Повторить проверку с отключенным кешем и замедленной сетью.

## 4. Пагинация не меняет демонстрационную выдачу и не учитывает страницу из URL

**Приоритет:** средний. **Связь с предыдущим отчетом:** Д11. **Основание:** пункт 3.6 ТЗ — интерактивные элементы реализуются с демонстрационными данными.

**Страница:** [Новости и события](https://bhenergy.github.io/ystu-frontend/pages/news-events.html).

**Как воспроизвести:**

1. Открыть страницу и запомнить отображаемый набор карточек.
2. Нажать номер 2 в пагинации.
3. Сравнить карточки до и после переключения.
4. Отдельно открыть [news-events.html?page=2](https://bhenergy.github.io/ystu-frontend/pages/news-events.html?page=2).

**Фактически:** выделенный номер меняется с 1 на 2, но набор карточек остается прежним. При открытии URL с `page=2` выбранной снова отображается страница 1. Номер при инициализации берется из исходного `aria-current`, а параметр URL не учитывается.

**Где исправлять:** [src/js/components/pagination.js, строка 7](https://github.com/BHEnergy/ystu-frontend/blob/09dc42812ee3a0bfcd1c150778b67afb5584f972/project-ystu-frontend/src/js/components/pagination.js#L7), а также связь компонента с демонстрационной выдачей.

Отчет разработчика честно описывает текущее ограничение. Однако наличие события `pagination:change` само по себе не показывает переключение набора записей. Реальная выборка из базы относится к интеграции; демонстрационное поведение интерфейса требуется на этапе верстки. Для проверки достаточно нескольких согласованных демонстрационных страниц с различающимся содержимым; создавать 16 искусственных наборов не требуется.

**Что требуется:** связать выбранный номер с демонстрационной выдачей; согласовать число страниц с объемом демонстрационных данных; синхронизировать выбранный номер, содержимое и URL. Проверить совместимость с фильтрами и поиском. Если заказчик согласует передачу только визуального переключения номера, отдельно зафиксировать это исключение; считать его уже согласованным нельзя.

**Критерии закрытия:** номера и стрелки меняют набор карточек; выбранный номер соответствует выдаче; прямой URL открывает соответствующее состояние; крайние состояния работают; применение фильтра не оставляет пустую недопустимую страницу.
